# LongNovelInsight v0.4.0 — Data Model

This document defines the current ownership and persistence meaning of LongNovelInsight records.
SQLModel classes under `backend/models/`, the ordered migrations in `backend/migrations.py`, and
the running SQLite schema are the exact field/constraint authority.

See [ARCHITECTURE.md](ARCHITECTURE.md) for component boundaries and
[ANALYSIS_RUN_CONTRACT.md](ANALYSIS_RUN_CONTRACT.md) for current versus legacy analysis provenance.

## Relationship Summary

```text
ModelProvider 0..1 <--- * Topic
Topic 1 --- 0..1 TopicProviderConfig
Topic 1 --- * Work
Work 1 --- 0..1 Document
Document 1 --- * Chapter
Document 1 --- * Chunk
Chapter 0..1 --- * Chunk

Topic 1 --- * AnalysisRun
AnalysisRun 1 --- * LocalExtraction
LocalExtraction 1 --- * ExtractedAtom
AnalysisRun 1 --- * AnalysisOutput
AnalysisRun 1 --- * AnalysisArtifact

Topic 1 --- * ChatSession
ChatSession 1 --- * ChatMessage
ChatSession 1 --- * RetrievalTrace

Topic 1 --- * GlobalEntity
GlobalEntity 1 --- * EntityMention
Work 1 --- * EntityMention
Topic 1 --- * GraphSnapshot
Topic 1 --- * TimelineItem
Topic 1 --- * CrossWorkRun

Topic 1 --- * Job --- * JobItem                 (deprecated executor records)
Chunk 1 --- 0..1 chunk_fts row                  (FTS5, application-managed)
```

Topic ownership is repeated on derived rows to enforce local scope efficiently. Work ownership for
source data is reached through `Document.work_id`. AnalysisRun Work ownership is persisted in
`chunk_selection_json.work_id`; there is no direct `work_id` column on AnalysisRun in v0.4.

## Shared Conventions

- Primary IDs are UUID strings generated by the application.
- Timestamps are timezone-aware UTC values at creation; SQLite stores SQLModel datetime values.
- Structured collections are stored as JSON text in `*_json` or similarly named text columns.
- Foreign-key enforcement is enabled for every pooled SQLite connection.
- Application services perform explicit scoped deletion; callers must not assume every relationship
  has a database `ON DELETE CASCADE`.
- Historical nullable fields are preserved for migration compatibility. Runtime services apply
  stricter invariants to newly created records.

## Workspace and Provider Records

### `topic`

One story universe or research workspace.

| Field group | Meaning |
| --- | --- |
| `id`, `name`, `description` | Identity and user metadata |
| `provider_id` | Optional bound ModelProvider |
| `status`, `storage_bytes` | Aggregate UI state and sum of persisted source Document byte sizes |
| `created_at`, `updated_at` | Lifecycle timestamps |

Topic creation also creates a deterministic default Work. Legacy Topic-level source and analysis
routes resolve that Work.

### `work`

One novel or volume inside a Topic.

| Field group | Meaning |
| --- | --- |
| `topic_id`, `title`, `subtitle`, `author` | Ownership and bibliographic metadata |
| `series_index` | Optional ordering inside a series |
| `description`, `metadata_json` | User/extended metadata |
| `status` | Work ingestion/analysis state |

A Work may have zero or one Document. Deleting a non-empty Work is intentionally rejected in the
current API rather than silently cascading source and derived data.

### `model_provider`

Local OpenAI-compatible provider configuration.

| Field group | Meaning |
| --- | --- |
| `name`, `provider_type`, `base_url` | Provider identity and endpoint |
| `api_key` | Credential stored locally and omitted from read responses |
| `model_name`, `context_window`, `max_output_tokens`, `temperature` | Provider defaults; zero/empty values allow preset/effective fallback |
| `is_default` | Legacy/default-provider selection aid |

API responses expose `masked_api_key`, not the stored credential.

### `topic_provider_config`

Optional one-to-one Topic overrides for provider, base URL, model, context window, output limit,
temperature, thinking mode, reasoning effort, analysis parallelism, and recommended profile.
Effective configuration resolves Topic override, then provider value, then detected preset/model
fallback where supported.

## Source Records

### `document`

One uploaded TXT or EPUB source. Important fields are `topic_id`, nullable historical `work_id`,
original/stored filenames, `file_type`, content type, encoding, byte/character counts,
`storage_path`, `metadata_json`, and status.

Current uploads always set `work_id`. The nullable column permits legacy databases to be backfilled
without losing data. The v0.4 schema enforces uniqueness by Work rather than the historical
one-Document-per-Topic constraint.

### `chapter`

A parsed source chapter. It carries Topic/Document ownership, document-local `chapter_index`, title,
character offsets/count, optional EPUB `source_href` and `nav_order`, and optional metadata JSON.

### `chunk`

A bounded analysis/retrieval unit. It carries Topic/Document ownership, optional Chapter ownership,
chapter-local `chunk_index`, optional `chapter_index`, text, source character offsets, estimated
tokens, and `source_locator_json`.

`source_locator_json` maps the normalized chunk back to TXT offsets or EPUB href/navigation data.
It is evidence provenance, not an external URL.

### `chunk_fts`

An SQLite FTS5 virtual table maintained by parser/search services. It indexes source chunk text and
titles and has no foreign key. CJK keyword fallback remains available when tokenization is not
sufficient.

## Authoritative Analysis Records

### `analysis_run`

The execution record for new analysis.

| Field group | Meaning |
| --- | --- |
| `topic_id`, `mode`, `status` | Scope and lifecycle |
| `requested_types_json` | Requested atom/output families |
| `chunk_selection_json` | Selected chunk metadata, including current `work_id` |
| `effective_config_json` | Provider/model snapshot for reproducibility |
| `progress_current`, `progress_total` | Aggregate progress |
| extraction/merge/final totals and succeeded/failed/skipped fields | Stage outcomes |
| prompt/completion/total tokens, `model_used` | Cumulative returned usage |
| `metadata_json`, `error_message` | Usage breakdown, warnings, recovery/retry metadata |
| started/finished/created/updated timestamps | Lifecycle times |

`job_id` is nullable historical compatibility data and is not used as the new execution bridge.
Work runs are identified through `chunk_selection_json.work_id`.

### `local_extraction`

One selected Chunk's LLM extraction within one AnalysisRun. It records status, attempt count,
canonical parsed JSON, evidence/confidence, cumulative prompt/completion/total/reasoning/cache token
fields, attempts whose usage was unavailable, per-attempt usage JSON, model, error, and timestamps.

There is at most one current extraction record per selected run/chunk combination by service
invariant. Retry and resume update or reuse that record rather than creating an unrelated run.

### `extracted_atom`

A normalized fact derived from LocalExtraction. It carries AnalysisRun/Topic ownership, optional
extraction/chunk links, atom type, stable ID, canonical name/title/summary, structured content,
source chunk IDs, evidence quotes, confidence, and source ordering fields.

### `analysis_output`

A read projection consumed by the UI, retrieval, and chat.

- `run_id != NULL`: current AnalysisRun merge/final provenance.
- `run_id == NULL`: historical v1/Job-era output.
- `output_type` may be an internal `merge_*` row or a final family.
- `content_json` may be inline JSON or a compact AnalysisArtifact pointer.
- `source_chunk_ids`, `evidence_quotes`, confidence, and token fields support evidence/usage reads.

`job_id` remains only for compatibility. New product code must not create null-run final outputs.

### `analysis_artifact`

Metadata for analysis JSON larger than 64 KiB. It records Topic/optional Run ownership, artifact
type, owner table/ID, path relative to `data/`, byte size, and a compact SHA-256 fingerprint. The
corresponding file lives under `data/topics/{topic_id}/artifacts/`.

## Chat and Retrieval Records

### `chat_session`

A Topic-owned named conversation with creation/update timestamps.

### `chat_message`

A user, assistant, or historical system message. Besides content and usage, current pairs use:

- shared `turn_id`;
- shared session-local `sequence_index`;
- assistant `reply_to_message_id` pointing to the user message.

These fields remain nullable for old databases. `evidence_json` stores structured evidence or
legacy compatible data; `uncertainty` records an explicit answer limitation.

### `retrieval_trace`

A persisted debug trace with Topic scope, optional Chat session/message links, query, method, and
ranked results JSON. Traces created for Chat are deleted with their owning session/message through
explicit service cleanup.

### `embedding_cache`

A migration-created table reserved for optional local JSON vectors keyed by Topic, source type/ID,
and model. Semantic reranking and its provider remain disabled/not implemented in the current
product runtime, so normal v0.4 workflows do not populate this table.

## Cross-Work Records

### `global_entity`

The canonical Topic-wide entity registry. It stores type, canonical name, aliases, contributing
Work IDs, mention/evidence counts, confidence, merge strategy, and metadata. It is not partitioned
into independently versioned scoped registries. Rebuilds preserve IDs for identity-equivalent
groups when possible; graph snapshots containing removed entity IDs are invalidated.

### `entity_mention`

Evidence linking a GlobalEntity to one Work and a source record. It stores source type/ID, optional
Chunk/Chapter IDs, surface/evidence text, confidence, and metadata.

### `graph_snapshot`

A versioned Topic graph projection with graph type, normalized `scope_json`, nodes, edges,
statistics, and creation time. Scope is part of identity at the service layer: same-scope rebuilds
replace each other while All and selected-Work snapshots coexist.

### `timeline_item`

A Topic-owned, optionally Work-linked event projection with source atom ID, title/summary,
sequence/time labels, participants, locations, causes, effects, evidence, and confidence. Scoped
rebuilds replace rows only for selected Works.

### `cross_work_run`

A Topic-owned orchestration record with mode, status, timestamps, error, statistics, and warnings.
Requested Work scope is preserved in statistics/response metadata by the service contract; empty
scope means canonical All.

## Deprecated Compatibility Records

### `job` and `job_item`

These records belong to the deprecated parse/analysis Job executor. They retain lifecycle,
progress, item-type, message/error, and timestamp data so existing local databases and API clients
remain readable in v0.4.

They are not adapters to AnalysisRun, do not provide reliable current AnalysisOutput provenance,
and must not receive new frontend callers. Removal requires explicit migration scope.

## Migration and Integrity Rules

Database startup first creates absent current tables, then replays the ordered migration registry.
Notable repair rules include:

- source locator fields precede the v0.4 Document table rebuild so metadata is preserved;
- legacy Documents receive deterministic default Work ownership;
- legacy Chat rows receive best-effort turn/link/order backfill in stored row order;
- the historical Topic-unique Document constraint is detected through SQLite unique constraints;
- migrations are idempotent and stop on failure;
- foreign-key checks run after schema rebuilds, and connection-wide enforcement is restored.
- startup removes malformed or dangling character-relationship snapshots using the live entity
  registry and backfills every Topic's cached source-byte aggregate from Document rows.

Tests for migration behavior use genuine historical DDL and temporary SQLite files. They validate
data preservation, replay, FTS, foreign keys, Work/Chat backfills, and failure-stop ordering.
