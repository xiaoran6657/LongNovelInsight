# LongNovelInsight v0.4.0 — Multi-Work Analysis and Runtime Hardening

> **Release Date:** 2026-07-13
> **Status:** Released.
> **Tag:** `v0.4.0`

---

## Goals

Make a Topic a reliable multi-volume analysis workspace while preserving existing local data and
legacy single-Document workflows. v0.4 adds explicit Work ownership, deterministic cross-work
views, one authoritative analysis lifecycle, safer chat and database recovery, and stronger
frontend failure isolation without adding cloud services, external infrastructure, or LLM
frameworks.

Because v0.3.1 was documented but never tagged, v0.4.0 also includes its analysis stability,
truncation handling, retry, and cumulative token-accounting improvements relative to the latest
published tag, v0.3.0.

## Highlights

### Multi-Work Topics

- A Topic can contain multiple ordered Works, with at most one TXT or EPUB Document per Work.
- Work-scoped upload, parse, chapter, chunk, metadata, search, retrieval, and analysis APIs keep
  source and result provenance isolated by volume.
- Existing single-Document Topics are migrated to a deterministic default Work. Topic-scoped
  source and AnalysisRun routes remain compatibility facades over that Work.
- Work source files include the Work ID so re-upload and cleanup cannot collide across volumes.

### Cross-Work Views

- Deterministic entity resolution merges compatible atoms by stable ID, canonical name, aliases,
  and normalized names without making an LLM request.
- Relationship graph snapshots use relation atoms with event co-occurrence fallback and retain
  evidence links to source Works.
- Timeline items are ordered by Work series index, chapter, and chunk.
- Empty Work scope is the canonical All view. Scoped graph and timeline rebuilds no longer replace
  unrelated or canonical materializations.
- The frontend adds Work management, Work selection, a cross-work build dashboard, entity
  registry, relationship edge table, and timeline view.

### Authoritative AnalysisRun Lifecycle

- New analysis uses Work-scoped AnalysisRun creation, status, cancellation, retry, resume, and
  run-linked outputs.
- Topic-level AnalysisRun creation resolves one default Work and never mixes chunks from multiple
  Works.
- A numeric token estimate is required before the frontend's provider-credit confirmation and
  create action.
- Startup recovery marks orphaned `running` rows failed and resumable without calling the LLM;
  intentional `pending` rows remain unchanged.
- A process-local executor registry prevents duplicate same-process starts and permits at most one
  active analysis executor per Topic.
- Lifecycle, initial execution, and retry/resume reconstruction are split into domain services
  behind the existing router-facing facade.

Legacy v1 synchronous, v1 asynchronous, single-type, and Job/JobItem routes remain callable for
v0.4 compatibility but are deprecated in OpenAPI. The frontend no longer calls them. Existing
historical AnalysisOutput rows remain readable.

### Analysis Stability and Usage Accounting

- Transport errors, truncated JSON, and provider output-length exhaustion receive explicit error
  classification and adaptive retry behavior.
- Retry token limits can escalate to 16,384 tokens, with rate-limit, transport, and JSON failures
  using different backoff policies.
- Prompt, completion, reasoning, cache-hit, and cache-miss usage accumulates across attempts;
  attempts without returned usage are reported rather than estimated as zero-cost success.
- Cost estimates incorporate configured output limits, analysis mode, retry risk, and thinking
  mode. Merge and final projection remain deterministic and make no LLM request.

### Chat Correctness

- Edit and resend generates the replacement response before the atomic database replacement, so a
  failed provider call preserves the original exchange.
- New user/assistant pairs share an explicit turn ID and sequence index; assistants link directly
  to the user message they answer.
- Session reads use stable ordering, and delete/resend targets the linked pair rather than relying
  on timestamps.
- Existing databases receive deterministic best-effort linkage backfill for historical messages.

### Database and Migration Safety

- Startup migrations now run through an ordered, replayable, Engine-scoped registry of idempotent
  functions.
- Old-schema fixtures exercise the production migration path, including Document ownership and
  chat linkage upgrades.
- SQLite foreign keys are enabled for every pooled connection.
- Topic, Document, chat, and cross-work cleanup paths were corrected under actual foreign-key
  enforcement.

### Frontend Reliability and Maintainability

- Analysis output content is normalized defensively, malformed nested items are filtered, and an
  unexpected output-card failure does not hide other results.
- AnalysisOutputCard remains the stable import facade while data helpers, evidence primitives, and
  output-family renderers live under the analysis feature boundary.
- Topic Detail and Chat share centralized TanStack Query key factories, including response-shape
  options and scoped invalidation rules.
- E2E/config files participate in strict typecheck and lint. Pure-logic tests cover selection,
  formatting, query keys, and analysis-output normalization.
- Vite, React Router, Babel, and js-yaml security updates leave `npm audit` at zero known
  vulnerabilities.

## API and Compatibility

- The current FastAPI schema contains 83 documented method/path operations.
- Exact request and response schemas remain available at `/docs` and `/openapi.json`; the complete
  human endpoint map is [API.md](../API.md).
- No intentional breaking change is introduced for v0.3.0 local data or legacy single-Document
  clients.
- Non-empty Work deletion returns `409`; deleting the Topic remains the supported full cleanup
  operation.
- New integrations should use explicit Work routes and the AnalysisRun lifecycle rather than
  deprecated Job or v1 executor routes.

## Upgrade from v0.3.0

1. Back up the local `data/` directory before changing application versions.
2. Update to the eventual v0.4.0 release commit when it is published.
3. In `backend/`, activate the `LongNovelInsight` Conda environment and run
   `pip install -e ".[dev]"`.
4. Start the backend once. Startup creates absent current tables, runs the ordered idempotent
   migrations, backfills legacy Work/chat ownership, and recovers interrupted AnalysisRuns. It
   does not automatically call an LLM.
5. In `frontend/`, run `npm install`, then start the Vite application normally.
6. Confirm `/api/health`, existing Topics, provider bindings, Documents, and historical analysis
   outputs before starting new paid analysis.

The migration path preserves existing local records. A permanent migration-version ledger is not
used in v0.4; repair-capable migration functions are intentionally replayable on startup.

## Known Limitations

- Analysis execution ownership is process-local. Running multiple backend processes or Uvicorn
  workers against one SQLite database is unsupported.
- The relationship graph is an edge-table MVP; interactive graph visualization is deferred.
- Timeline pagination and expanded evidence controls are deferred.
- Work estimates are token-based, not currency-based, because provider pricing is not modeled.
- Legacy chat linkage backfill is best-effort when historical rows have indistinguishable ordering.
- Retry token totals are cumulative, but complete historical `attempt_usage_json` merging remains
  deferred.
- Browser Playwright tests mock API responses. The default backend suite includes an isolated
  upload/parse/AnalysisRun smoke with only the external LLM extraction boundary mocked.
- The opt-in live-provider smoke was not run during release validation because it can spend real
  provider credit.
